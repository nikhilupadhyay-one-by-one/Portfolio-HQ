02Three rules the projects share

Different problems, same instincts. These are the decisions that repeat across all three, and the reason the code looks the way it does.

Offline is the default, not the fallback

LocalLLM runs int4 weights on the laptop's own NPU. NetPulse ships an IEEE OUI table so it can name a device vendor with the Wi-Fi off. Guard needs the standard library and one dependency. If a tool only works when the network does, it is not a tool you can use during an incident.

A notification is a hint, not a fact

The OS says a file "was modified" several times per save. Guard waits 400 ms for the flurry to stop, re-hashes the file, and records nothing if the bytes match. NetPulse treats a negative counter delta as zero rather than reporting a multi-gigabyte spike. Verify, then report.

An alert you can't read isn't an alert

Every Guard event carries a severity and the reason it earned it — permissions changed to executable, not EVENT_MOD. NetPulse's ping ends in a plain-language verdict. The work is only finished when the output explains itself to someone who wasn't watching.

How the two halves meet

Decisions worth arguing about

Two languages, one deliberate seam

C++ owns the tray icon and the password gate; Python owns the model and the windows. They speak over a loopback TCP socket — chosen over named pipes, whose API diverges between Windows and Linux, and over gRPC, which is a code-gen step and a dependency to buy "the password was right."

SHA-256, written out by hand

v1 compared the password to a string literal and had a note about adding a Caesar cipher. v2 carries a self-contained FIPS 180-4 implementation and a per-install random salt, so the binary needs no OpenSSL and the password is never stored anywhere in any form.

One answer to "where do I live"

The gate resolves its own executable path — GetModuleFileNameW on Windows, /proc/self/exe on Linux — and hands it to Python as argv[1]. Both halves agree on the install root instead of each guessing from the working directory.

int4 weights, because the target is a laptop

Models come from the OpenVINO Hugging Face org already quantised: Qwen2.5-1.5B as the default that must be present on first run, Qwen3-8B and a 3B coder model as options. Device choice — CPU, GPU or NPU — belongs to the user at load time, not to me at build time.

The split that makes it work

Decisions worth arguing about

Read the counters, don't scrape the window

Every adapter keeps a cumulative byte count the OS maintains, and Task Manager draws its graph from exactly those numbers. psutil.net_io_counters() reads the same source. The rate is a finite difference, which needs no admin rights and behaves identically on all three platforms.

Parse the output, don't print it

Windows prints round-trip time before the address; Unix prints it after; both get translated into the user's language. The parsers key off the numeric shapes that survive translation — =12ms, ttl=115 — and pull each field independently. Captured output from a Spanish-locale Windows box is in the test suite.

MAC addresses without raw sockets

The sweep pings the whole subnet concurrently, which makes the OS resolve each responder's hardware address, then reads the ARP table where those resolutions now sit and joins on IP. Vendors come from a bundled IEEE OUI table, so discovery works with no internet at all.

Nothing blocks the interface

Scans, traces and socket enumeration run on QThread workers that push rows back through signals, so results appear as they are found and every long operation can be stopped mid-flight. Child processes launch with CREATE_NO_WINDOW, so no console flashes on screen.

The arithmetic that has to be right

core/bandwidth.py · counter deltas
@staticmethod
def _delta(current: int, previous: int) -> int:
    """Difference between two counter readings, ignoring wraps and resets.

    Adapter counters are unsigned and reset when the interface is disabled
    or the driver reloads. A negative delta means one of those happened, and
    the honest answer is zero rather than a huge spike.
    """
    delta = current - previous
    return delta if delta >= 0 else 0

A note the tool also prints on screen

The port scanner is for hosts you own or have written permission to test. Scanning other people's systems is unlawful in many places, including under the Information Technology Act in India and the Computer Fraud and Abuse Act in the United States.

The problem, stated precisely

A naive directory watcher is unusable, and it fails in a specific way. The operating system reports that a file was modified constantly — every save, every backup sweep, every metadata poke, usually several times for one edit. Log all of it and you get thousands of lines a day that nobody reads. Guard treats the notification as a hint: it waits for the flurry to stop, re-reads the file, hashes it, and compares against what it recorded last time. Only a real difference becomes an event. That one decision is the difference between an audit log and a firehose.

Raw events in, verified changes out

Decisions worth arguing about

A fingerprint, not an event

Each file reduces to size, SHA-256, permission bits, mtime and entropy. Comparing two fingerprints answers every question the tool asks: did the content change, did the permissions change, did the content become unreadable.

Entropy jumps, not volume

The ransomware check counts one thing — files that were readable and now are not. An earlier version counted every busy file and asked what fraction looked encrypted; a compile writes hundreds of files and drowns that signal. Files already near-random (.zip, .jpg) are excluded, so copying in a photo library is not an incident.

Ignoring its own tail

Guard's database lives on disk, often inside the folder being watched. Without an explicit skip, writing an event causes a file change, which causes an event, which causes a write. guard.db is on the ignore list for that reason specifically.

One connection, one lock

Three threads touch SQLite: the observer, the processing loop and the dashboard's web server. Guard holds a single connection with a lock around every use, in write-ahead logging mode so the dashboard can read while the watcher writes. One connection per thread would be slightly faster and considerably harder to be sure about.

The measurement everything rests on

guard.py · section 2, fingerprints
def shannon_entropy(data: bytes) -> float:
    """Average information per byte, in bits.

    The formula is -Σ p·log₂(p) over how often each byte value appears.
    A file of all zeroes scores 0. English prose scores about 4.5.
    Compressed or encrypted data is close to the 8.0 ceiling, because
    every byte value is equally likely.

    That last property is the useful one: when a text document's entropy
    jumps from 4 to 7.9, something encrypted it.
    """
    if not data:
        return 0.0

    total = len(data)
    entropy = -sum(
        (count / total) * math.log2(count / total)
        for count in Counter(data).values()
    )
    return entropy if entropy else 0.0

Severity notation

✕ critical

! warning

A binary changed, a file was deleted or truncated. shrank from 48.2 KB to 12 B

+ notice

A config file, a new file, a rename. created a configuration file

· info

Everything else. contents changed

Limits worth knowing

Guard sees what changed, not who changed it — attributing a write to a process needs auditd, ETW or FSEvents with elevation, which is a much larger piece of work. The ransomware check is a heuristic, and heuristics are wrong sometimes: encrypting a folder of your own files on purpose will trigger it. It is a smoke alarm, not a verdict. Symbolic links are not followed.

08Four bugs worth keeping

Each of these has a test written for it, and the test says in its docstring that it exists because of the bug. They are here because the shape of a bug says more about how someone works than a list of frameworks does.

Silent failure · Guard

The first ransomware alert never fired

The burst detector has a cooldown so one attack doesn't produce two hundred alerts. The cooldown used 0.0 as the marker for "never alerted yet."

On Linux, time.monotonic() counts from system boot — so 0.0 is a real timestamp, not a sentinel. During the first minute of uptime, the very first alert looked like a recent one and was suppressed. Nothing crashed. Nothing logged. The alarm simply did not go off, in exactly the window where a machine that just rebooted is most interesting.

The test that now guards it

test_the_first_alert_is_never_swallowed
     _by_the_cooldown
FIX

Use None for "never", not a value the clock can legitimately return. A sentinel has to be outside the domain of real values.

Masked signal · Guard

Ordinary work could hide an attack

The first ransomware heuristic counted every file that changed in the window and asked what fraction of them looked encrypted. It sounded reasonable.

It failed twice over. A compile writes hundreds of ordinary files and drowns the signal in the denominator — and nine innocent edits just before a sweep were enough to push the fraction under its threshold, so the alert never fired at all. The fraction test also did no real work: build output is plain readable text, so it was never the thing being measured.

The test that forced the redesign

test_ordinary_activity_beforehand
     _cannot_mask_a_sweep
FIX

Count one thing instead: files that were readable and now are not. No denominator, no dilution. Already-random file types are excluded entirely.

17s to 0.09s · NetPulse

Rejecting a subnet took seventeen seconds

The device sweep refuses networks that are too large to scan. The check built the address list first, then measured it.

Handed a /8, it expanded 16.7 million addresses into memory before concluding they were too many to use. The answer was correct and the test suite took seventeen seconds to get it.

Result

pytest   before  17.00s
         after    0.09s
FIX

Read num_addresses — which the network object already knows — before generating anything. Ask the cheap question first.

Near miss · Guard

The noise filter almost swallowed chmod +x

The filter that makes Guard usable drops anything whose hash is unchanged. A permission change doesn't touch a single byte.

So the most security-relevant thing a file can undergo — gaining the execute bit — would have been discarded by the feature that exists to reduce noise. The fix is in the fingerprint design itself: permissions are part of the fingerprint, so "unchanged" means unchanged in every field, not just content.

The test that now guards it

test_permission_change_alone
     _is_still_reported
FIX

Compare the whole fingerprint, not the hash. A filter should only ever remove things it can prove are identical.

Self-contained SHA-256 with a per-install salt. Both halves agreeing on the install root. A generation loop that holds its own chat history and streams tokens back. Next: the Qt6 tray shell, the PySide6 mode windows, and Piper for speech.
